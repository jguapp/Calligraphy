Part I · Why Calligraphy exists

1.1 · What a "background job" actually is

Start from a web request. A user clicks save; the server has, by convention and by timeout, a couple of seconds to answer. Anything that must happen but doesn't fit in that window — a fifteen-second page fetch, a minute of CPU, a call to a flaky third party that needs retries — has to happen somewhere else, later, reliably. That triple is the whole definition of a background job: work detached from the request that created it, carrying an obligation to eventually happen anyway.

The word doing all the work in that sentence is reliably. Detaching work from a request is trivial — one line in any language. Detaching it without losing it when the process restarts, the handler throws, the machine dies, or the same message arrives twice is an entire engineering discipline, and it's the one this document teaches.

1.2 · The four gaps that made it concrete

Calligraphy was built as the asynchronous tier for Booklet, a read-it-later platform whose own source comments document four places where background work is either blocking a user or quietly droppable:

WhereBooklet's own words / behaviorThe missing property
Article extractionRuns on the save request: up to a 15-second page fetch, Readability parsing, and as many as 30 image downloads while the user watches a spinner. A failure is recorded and the work is simply gone.Detachment + retry
Embedding indexingA fire-and-forget promise: "failures are logged and dropped… a backfill script re-attempts anything missed." The recovery plan is a human remembering a script.Durability
Webhook delivery"At-least-once, no retry queue yet — a receiving endpoint being briefly down loses that one delivery." (As written it is actually at-most-once.)Retry with backoff

Four features, one missing piece of infrastructure. That is the entire product definition of Calligraphy — and the reason it is a separate service with a public API rather than a Booklet module. Infrastructure that imports your product's code isn't infrastructure; it's a bigger product.

Decision
Calligraphy contains none of Booklet's business logic and never touches Booklet's database. For work whose logic must stay in Booklet (extraction needs Readability and a DOM), Calligraphy holds the schedule, the retries, and the dead-letter queue, and calls Booklet back over signed HTTP — the Cloud Tasks model. That boundary is what keeps it reusable by any application, and it is why every example in this document speaks plain HTTP and JSON at the edges.

1.3 · Why not an existing queue?

Sidekiq, Celery, BullMQ, River, and a dozen others exist and are good. Two honest reasons this was built instead of adopted. First, the project is a demonstration of understanding — the point is to be able to explain every mechanism, which you can only fully do for machinery you built and measured. Second, and more transferable: the shape here (queue in Redis, record in Postgres, workers in Go, HTTP at the edge) is roughly what you'd converge on assembling any of those tools into a real deployment anyway, so building it once, honestly, teaches what all of them are doing under their APIs. Where an existing tool genuinely differs (RabbitMQ's native acks, Kafka's replayable log), Part V says so and says why the trade fell where it did.

Part II · The shape of the system

2.1 · Three sentences, then everything else

The whole architecture fits in three sentences, and every other page of this document is a footnote to them:

Redis moves the work. Jobs travel as self-contained envelopes through Redis Streams, so dispatching work never requires a database read. Redis is fast, and it is allowed to be merely fast because it is not the record.

Postgres records the truth. Every job, every attempt, every state change lives in four tables, forever. When Redis and Postgres disagree — and in crash windows they briefly can — Postgres wins, and three repair sweeps exist to make it so.

gRPC carries only control. Worker stats stream up; drain/pause/resize commands stream down. Jobs never travel there — a control channel that grows job-delivery ambitions becomes a second, worse queue.

2.2 · The pieces and where they live

cmd/
  calligraphy-api      HTTP API + recovery leader + gRPC control plane
  calligraphy-worker   the fleet: pool, runner, handlers, metrics
  calligraphy-bench    the load generator with honesty properties
  calligraphyctl       operator CLI (a plain HTTP client, on purpose)
internal/
  job/        the domain: record, state machine, error taxonomy   (imports nothing)
  store/      Postgres: fenced writes, batched recording           (imports job)
  queue/      Redis Streams: priorities, delayed set, DLQ, leases  (imports job)
  worker/     bounded pool + runner: claim→execute→record→ack      (imports all three)
  recovery/   reaper, promoter, repair sweeps (leader-elected)
  handler/s   the one-method Handler interface + built-ins
  api/ control/ scale/ metrics/ retry/ config/

The dependency arrows only point down. internal/job imports nothing, which is what lets the state machine be tested with no database or queue in sight; store and queue each import only job, so neither knows the other exists; the worker composes all three. When you read the code, read it in that order — it's the order the system was built in, one merged PR per layer.

2.3 · Why two stores instead of one

A queue alone can't answer "what happened to job X yesterday" — that's a SQL question. A database alone makes a poor queue — polling a table for work means either hammering it or adding latency, and row-lock contention under many concurrent claimants gets ugly. Using each for what it's good at costs one real thing: seams. Every operation that writes to both (submit = INSERT then XADD; retry = UPDATE then ZADD) can crash between the two writes, and each of those windows needs a name and a repair mechanism. Part XII enumerates all four; Parts IV and V teach the store-level machinery the repairs are built from.

Trade-off
Two stores means two things to operate and a class of repair machinery a single-store design wouldn't need. The alternative — Postgres-only with SELECT … FOR UPDATE SKIP LOCKED — is legitimate at small scale and simpler. Streams were chosen because the consumer-group machinery (per-message acks, idle-time reclaim) solves the crashed-worker problem natively, and because the application this serves already operates Redis. Reasonable people pick the other branch; the point is to know you're choosing.

Part III · Go: concurrency as a language

3.1 · The problem concurrency solves here

A worker's day is mostly waiting. An article.analysis job waits on Postgres to return the article; an http.callback job waits on someone else's server; even a CPU-heavy job waits on the database to record its result. If a worker ran one job at a time, the CPU would idle through all of that waiting — the I/O benchmark in Part XIV puts a number on it: one worker at concurrency 1 moves 16 jobs/s, the same worker with a concurrent pool moves 123. The entire gap is waiting that stopped blocking the line.

So the real requirement is: run many jobs at once, but never more than a chosen number, and be able to stop cleanly. Everything this part teaches — goroutines, channels, select, context — exists to make that sentence implementable in about a hundred lines.

3.2 · Goroutines: threads, priced differently

A goroutine is a function running concurrently with the rest of the program. Conceptually it is a thread; economically it is not. An OS thread costs a megabyte-ish of pre-reserved stack and a kernel context switch (microseconds, through the scheduler) every time it blocks. A goroutine starts with a ~2 KB stack that grows and shrinks as needed, and is scheduled by the Go runtime itself in user space.

The runtime's scheduler is an M:N multiplexer: it runs N goroutines on top of M OS threads, where M is roughly your core count (GOMAXPROCS). Three letters name the moving parts in every writeup you'll find: G (a goroutine), M (an OS thread), P (a "processor" — a scheduling token, one per core, each with its own run queue of Gs). An M must hold a P to run Go code; idle Ps steal work from busy Ps' queues, so cores stay fed without a global lock.

The detail that makes worker pools natural in Go: blocking is cheap. When a goroutine blocks on a channel or a network read, the runtime parks that G and hands its M/P to another G — no kernel involvement for channels, and network I/O goes through an event loop (the netpoller) so a thousand goroutines waiting on a thousand sockets consume one epoll, not a thousand threads. This is why Calligraphy can say "one goroutine per in-flight job" and mean it literally, where a C++ or Java design of the same shape would reach for an explicit event loop or a thread pool with queued callbacks.

3.3 · Channels and select: communication as synchronization

A channel is a typed conduit: ch := make(chan int) makes one, ch <- 3 sends, v := <-ch receives. The crucial property is that an unbuffered channel is a rendezvous — the send blocks until a receiver is ready, and vice versa — so passing a value is also a synchronization event. You don't lock a mutex around the data and signal a condition variable; handing the value over is the signal. That's the slogan "don't communicate by sharing memory; share memory by communicating."

A buffered channel (make(chan T, n)) decouples the two ends by up to n values. And select waits on several channel operations at once, proceeding with whichever becomes ready first — it is the tool for "wake up when a job finishes, or a timer ticks, or shutdown begins, whichever happens first," which is precisely the wait in the pool loop below.

Two idioms from that loop worth naming now, since they read strangely the first time:

// idiom 1: closing a channel broadcasts. Every receiver of a closed
// channel unblocks immediately -- close(done) wakes all waiters at once.

// idiom 2: non-blocking send. Try to send; if nobody's ready and the
// buffer is full, do nothing rather than wait.
select {
case p.completions <- struct{}{}:
default:
}

Calligraphy also uses sync/atomic for the two hot counters (target, active) — single-word values read and written from many goroutines, where a mutex would be ceremony — and sync.WaitGroup to wait for "all in-flight goroutines are done" at drain. Those three primitives (channels, atomics, WaitGroup) are the entire concurrency toolbox this codebase needs.

3.4 · context.Context: cancellation as a tree

Go has no way to kill a goroutine from outside — deliberately, because a killed thread leaves locks held and invariants broken (this is why Thread.stop() is deprecated in Java). Cancellation is instead cooperative, and context.Context is its carrier: a value passed as the first argument to everything, carrying a done-channel that closes when some ancestor decides to cancel. Contexts form a tree — context.WithCancel(parent), WithTimeout, WithCancelCause — and cancelling a node cancels its whole subtree. Every blocking API in the codebase (pgx queries, go-redis calls, http.Request) accepts a context and returns early when it's cancelled, so cancellation propagates through I/O, not just through polite loops.

The runner gives each job execution its own timed context (ExecTimeout, default 5m); the pool receives one context for fetching and a second for jobs; a cancelled job can distinguish why it died via context.Cause — which mattered enough to produce one of the ten bugs in Part XV (a cancelled job read the cause from the wrong context and retried instead of cancelling).

3.5 · The bounded pool, line by line

internal/worker/pool.go

Here is the heart of the worker, minus logging and error backoff:

for fetchCtx.Err() == nil {
    free := int(p.target.Load() - p.active.Load())
    if free <= 0 {
        // Full. Sleep until a completion, a resize tick, or shutdown.
        select {
        case <-fetchCtx.Done():
        case <-p.completions:
        case <-time.After(250 * time.Millisecond):
        }
        continue
    }

    n := min(free, p.batchMax)
    deliveries, err := p.fetch(fetchCtx, n)   // blocking XREADGROUP, ≤ n
    ...
    for _, d := range deliveries {
        p.active.Add(1)
        p.wg.Add(1)
        go func() {
            defer func() {
                p.active.Add(-1)
                p.processed.Add(1)
                p.wg.Done()
                select {                       // nudge the loop awake
                case p.completions <- struct{}{}:
                default:
                }
            }()
            p.run(jobCtx, d)
        }()
    }
}
p.wg.Wait()

Read it as a contract. free = target − active is computed before every fetch, and the fetch never asks Redis for more than free. Consequences, in order of importance:

The bound is structural. There is no path that creates a goroutine without incrementing active, so more than target jobs simply cannot run. Nobody audits a semaphore that's acquired in some places; the loop is the only entrance.

Backpressure falls out for free. When all slots are busy, the worker stops asking. Backlog therefore accumulates in Redis — where it is visible as queue depth, durable across a worker crash, and claimable by any other worker — rather than inside this process's memory, where it would be none of those things. The pool deliberately has no internal buffer channel of claimed work; Part V's lease machinery only has to cover jobs that are actually running, because claimed-but-parked jobs don't exist.

Resizing is a number, not an event. SetTarget is one atomic store. The loop re-reads target every iteration, so growth takes effect at the next fetch and shrinkage just means fetches pause until enough jobs finish. Nothing in flight is touched — which is what lets the control plane (Part VI) and the autoscaler resize a live worker mid-load.

The idle path is quiet. When the pool is full, the select parks the loop on three events. The completions channel exists only as a wake-up nudge — a finishing job does a non-blocking send, and if the buffer is full, fine: the loop is about to wake anyway. The 250ms timer is a belt-and-braces tick so a missed nudge costs a quarter second, never a hang.

3.6 · Two contexts, two-phase shutdown

internal/worker/worker.go

Pool.Run(fetchCtx, jobCtx) takes two contexts because shutdown has two distinct phases with a policy decision between them:

<-ctx.Done()                      // SIGTERM arrived
stopFetch()                       // phase 1: no new claims; drain begins

select {
case <-poolDone:                  // in-flight jobs finished on their own
case <-time.After(w.cfg.DrainTimeout):
    stopJobs(context.Cause(ctx))  // phase 2: cancel what's still running
    ...
}

Phase one cancels only the fetch context: the worker stops taking work but lets running jobs finish, for up to DrainTimeout (default 25s). Only if jobs outlive that does phase two cancel the job context, which every handler sees through its own execution context. A handler that ignores even that is abandoned to the reaper — the worker logs it and exits anyway, because the recovery machinery (Part XII) exists precisely so that an ungraceful exit is safe. Kubernetes' grace period is set to 40s > 25s so phase one usually wins (Part X).

One more containment detail lives in the runner: each job goroutine runs the handler under defer/recover. A handler that panics — nil map write, out-of-range index — does not take down the other seven jobs in the pool or the worker itself; the panic is caught, classified as its own outcome (OutcomePanicked), recorded, and retried with backoff like any transient failure. A worker process should die for infrastructure reasons, never because one payload found a bug in one handler.

Decision
No buffered channel of claimed jobs between fetcher and executors, even though that's the textbook worker-pool diagram. A buffer would smooth fetch latency, but every buffered delivery is a job that is claimed (its PEL entry ticking toward the lease timeout, Part V) yet not running — invisible to queue-depth metrics, lost to this process on crash, and un-claimable by an idle peer worker. The fetch-what's-free loop keeps "claimed" and "running" the same set, which makes the lease story in Part XII tell no lies.

Part IV · PostgreSQL: the truth machine

4.1 · What a database promises, without the acronym

Strip the ACID acronym to what it buys this system. Atomicity: a transaction's writes land together or not at all — the batcher (4.6) leans on this to make 128 job results durable as one unit. Consistency: declared rules (the status CHECK constraint, the unique dedupe index) cannot be violated by any sequence of writes. Isolation: concurrent transactions behave as if ordered — the claim UPDATE (4.4) is built directly on this. Durability: once COMMIT returns, the data survives a crash, because of the WAL (4.3).

Calligraphy's division of labor, stated once more precisely: Postgres holds the truth — every job's current status, payload, result, attempt history, lease bookkeeping — and Redis holds the motion. Every question that starts "what happened…" is a SQL query; every question that starts "what should run next…" is a stream read. When the two disagree, Postgres wins and the repair sweeps (Part XII) make Redis agree again.

4.2 · MVCC: readers and writers, out of each other's way

Postgres implements isolation with multi-version concurrency control. An UPDATE does not overwrite the row; it writes a new version of it, stamped with the writing transaction's ID, and leaves the old version in place for transactions that started earlier. Readers never block writers and writers never block readers — each transaction sees the newest version visible to its snapshot. (The garbage this generates — dead row versions — is what VACUUM exists to reclaim; a table like jobs, where every row is updated several times through its lifecycle, is exactly the shape autovacuum earns its keep on.)

Two writers, though, do contend: if two transactions UPDATE the same row, the second blocks until the first commits or aborts, then re-evaluates its WHERE clause against the new version. Hold that sentence — it is the entire mechanism behind claim arbitration in 4.4.

4.3 · The WAL: why commit means fsync

Durability is implemented with a write-ahead log: before any change touches the table files, a record of it is appended to a sequential log, and COMMIT returns only after that log has been fsync'd to disk. Table pages can then be written back lazily; after a crash, replaying the WAL reconstructs everything the log had. The performance shape this creates is the single most important fact for a write-heavy system: the cost of a commit is dominated by one disk flush, largely independent of how much data is in it. Ten one-row transactions pay ten flushes; one ten-row transaction pays one. Postgres already groups concurrent commits opportunistically (group commit), but an application that batches deliberately can do much better — that arithmetic is the entire case for 4.6.

4.4 · One UPDATE as an arbiter

internal/store/store.go — ClaimJob

Under at-least-once delivery (Part XIII), two workers will sometimes hold deliveries for the same job — a redelivery after a crash, a repair re-enqueue racing the original. Exactly one of them may run it. Calligraphy does not use an explicit lock, a lock table, or an advisory lock for this; it uses the WHERE clause:

UPDATE jobs SET
    status = 'RUNNING',
    worker_id = $2,
    lease_epoch = lease_epoch + 1,
    lease_expires_at = now() + make_interval(secs => $3),
    started_at = COALESCE(started_at, now()),
    attempt_count = attempt_count + 1,
    updated_at = now()
WHERE id = $1 AND status IN ('PENDING','RETRYING')
RETURNING lease_epoch, attempt_count, max_attempts, now()

Run this from two workers at once and MVCC (4.2) arbitrates: the second UPDATE waits for the first to commit, re-checks its WHERE against the new row version, finds status = 'RUNNING', matches zero rows. In Go that surfaces as pgx.ErrNoRows and the losing worker's whole handling is: ack the redundant delivery away and move on. "Zero rows affected" is not an error — it is the answer. The database's own concurrency control is the mutex, the arbitration is a single round trip, and there is no lock to leak if a worker dies mid-claim (the transaction just aborts).

Notice attempt_count increments at claim, not at completion. A worker that dies mid-attempt has still spent an attempt — counting at completion would give crashing jobs unlimited retries, and crashes are precisely what retry budgets exist to bound.

4.5 · Fencing: the lease_epoch column

Claiming solves who starts; fencing solves who may finish. The failure it exists for: worker A claims job X with a 30-second lease, then stalls — a long GC pause, a network partition, a laptop lid, anything. The lease expires; the reaper re-queues X; worker B claims it and runs it. Then A wakes up, finishes its copy, and writes "COMPLETED, result = …". If that write lands, B's later, correct write collides with it — or worse, A's stale result overwrites B's fresh one. A is a zombie: a process acting on ownership it lost.

The defense is a fencing token: a number that increases every time ownership changes hands, checked on every write. The claim UPDATE above does lease_epoch = lease_epoch + 1 — A claimed at epoch 6, so the reaper's requeue and B's claim move it to 8 — and every terminal write carries the epoch its writer believes it holds:

UPDATE jobs SET status = 'COMPLETED', result = $3, error = NULL,
    completed_at = now(), lease_expires_at = NULL, updated_at = now()
WHERE id = $1 AND lease_epoch = $2 AND status = 'RUNNING'

A's write arrives with epoch = 6, matches zero rows, and nothing happens. The zombie wasn't detected, wasn't killed, wasn't coordinated with — its write was simply void. Complete, fail, cancel, retry, dead-letter, and lease renewal all match on (id, lease_epoch, status = 'RUNNING'); the fenced-write counter (calligraphy_writes_fenced_total, Part VIII) counts how often the fence actually caught something. This is the standard remedy for the distributed-locks-with-leases problem — locks with timeouts are unsafe without a token the resource itself checks, and here the "resource" is the jobs row, which makes the check one predicate.

The same trick, run backwards, powers the reaper: when it re-queues an expired lease it also bumps the epoch, which revokes the old worker's write ability atomically with the decision to reassign. There is no window in which both the zombie and the new owner hold valid credentials.

Trade-off
Fencing gives Calligraphy exactly-once result persistence — at most one attempt's write wins — while execution remains at-least-once: worker A still ran its doomed copy, spent CPU, and produced any side effects the handler had. The fence protects the record, not the world; protecting the world is idempotency, and that boundary is drawn carefully in Part XIII.

4.6 · Batched recording: amortizing the flush

internal/store/batch.go

Recording an outcome takes three statements — update the jobs row, insert an attempt row, and (for retries) reschedule. At high throughput, paying a WAL flush per job (4.3) makes the database the bottleneck. The Batcher is a classic coalescing writer: outcomes go into a channel; one goroutine collects them and flushes a batch as one transaction whenever it holds BatchMaxSize ops (128) or BatchInterval elapses (20ms), whichever comes first. Size bounds the transaction; the interval bounds added latency. A failed flush retries once, then falls back to writing ops individually so one poisoned statement can't wedge the batch.

The interface seam matters more than the mechanism: the runner records through a store.Recorder, with SyncRecorder (write now) and Batcher (write soon) as the two implementations, switched by the CALLIGRAPHY_BATCH_WRITES flag. That flag is why the ablation benchmark (Part XIV) can measure batching's contribution honestly — and the measurement bit back: at one worker, batching lost 13% (adding latency nobody needed), and even at the full fleet it bought almost no throughput because the submission path, not recording, was the bottleneck on that host. The optimization is real; the bottleneck it optimizes just wasn't the live one there. It ships default-on (the multi-host deployments it exists for are write-bound), with the single-host verdict recorded honestly in Part XIV: measure yours.

Durability honesty: while an outcome sits in the batcher, the job's truth exists only in this process. The window is bounded (≤20ms + one flush), drain flushes everything before exit, and a SIGKILL inside the window loses only the record of an attempt, not the job — the lease expires and the reaper re-runs it, exactly like a crash one moment before the write. At-least-once absorbs the batcher's window into a window it already had.

4.7 · Details that earn their keep

Dedupe as a partial unique index. Submission idempotency (Part XIII) rests on ON CONFLICT (type, idempotency_key) WHERE idempotency_key IS NOT NULL DO NOTHING — a partial unique index, so jobs without a key opt out entirely. The API then re-reads the existing row and returns it with 200 (vs 201 for a fresh insert), so a client retrying a timed-out submit gets the same job back, not a twin.

Migrations embedded, under an advisory lock. Schema files compile into the binaries (//go:embed); every binary runs the migrator at boot inside pg_advisory_lock, so N processes starting against an empty database serialize politely and N−1 of them find nothing to do. Compose and Kubernetes then need no "run migrations first" orchestration step — any start order works.

jsonb is semantic, not textual. Payloads are stored as jsonb, which parses and canonicalizes: key order isn't preserved, whitespace is gone, 1e2 becomes 100. Comparing a stored payload to an incoming one byte-for-byte is therefore wrong — found the hard way (Bug 6, Part XV); the fix compares decoded values, not bytes.

Try it yourself
Watch arbitration and fencing with your own hands, no workers involved. Open two psql sessions (docker compose exec postgres psql -U calligraphy):

BEGIN;
UPDATE jobs SET status='RUNNING',

Part V · Redis: the moving parts

5.1 · What Redis actually is

Redis is a server holding data structures in memory — strings, hashes, sorted sets, streams — that you manipulate with commands over TCP. The architectural fact everything else follows from: command execution is single-threaded. One event loop reads commands from all clients and executes them one at a time. That sounds like a limitation and is actually the superpower: because operations on in-memory structures take microseconds, one thread sustains hundreds of thousands of them per second, and because nothing interleaves, every command is atomic by construction. No locks, no torn reads, no compare-and-swap loops. When 7 workers hammer XREADGROUP on the same stream (Part XIV's fleet run), Redis never hands the same entry to two of them within a group — not because of clever locking, but because there is no concurrency to defend against.

Persistence exists (RDB snapshots, AOF append logs with configurable fsync) but Calligraphy deliberately doesn't lean on it: Redis here is transport, and the design survives Redis losing everything — Part XII's repair sweeps rebuild queue state from Postgres, the truth (Part IV). This is a freeing decision: tuning Redis durability trades throughput for a guarantee the architecture gets elsewhere for free.

5.2 · Streams, from zero

A stream is an append-only log inside Redis. XADD mystream * k v appends an entry and returns its ID — 1723180800123-0, a millisecond timestamp plus a sequence number, so IDs are unique and totally ordered. Entries are read by ID range, and unlike pub/sub (fire-and-forget: miss it and it's gone), entries persist until trimmed. So far, a log.

What makes streams a work queue is consumer groups. A group (created with XGROUP CREATE) is a named cursor over the stream plus per-consumer bookkeeping. Its three verbs:

CommandWhat it does
XREADGROUP GROUP g c … >Hand the next unread entries to consumer c, advance the group cursor, and record each entry in the pending entries list (PEL): "delivered to c at time t, delivery-count n." Two consumers reading the same group never receive the same entry.
XACK g idRemove the entry from the PEL: work finished, bookkeeping closed.
XAUTOCLAIM g c min-idleScan the PEL for entries whose delivery is older than min-idle and hand them to consumer c, bumping their delivery count. This is how work escapes a dead consumer.

Read that table again as a systems statement: the PEL is a crash detector. Claimed-but-unacked work is exactly the set of entries in the PEL, each with a timestamp of when its consumer went quiet. A consumer that dies mid-job leaves its entries pending; their idle clocks tick; XAUTOCLAIM finds them. SQS calls this same idea a "visibility timeout" — the entry is invisible to others while claimed, and reappears if not deleted in time. Streams give you the machinery with the dials exposed.

5.3 · How Calligraphy maps onto streams

internal/queue/queue.go

The mapping, piece by piece:

Three streams, one per priority. calligraphy:stream:high|default|low, one consumer group (workers) on each. Priority is implemented in the fetch order, not in Redis: Fetch first drains high-then-default-then-low with non-blocking reads (Block: -1), and only if all three come back empty does it issue one blocking XREADGROUP on all three keys at once (up to 2s). Under backlog the non-blocking pass runs strict priority; when idle, the blocking pass wakes on whichever stream produces first — a wake-up race Redis doesn't arbitrate across keys, accepted because strict ordering matters under load, not in the instant an idle worker stirs.

Ack is XACK + XDEL, pipelined. A pure log would keep acked entries for replay; Calligraphy's stream is transport, and the job's history lives in Postgres. Deleting on ack keeps stream memory proportional to in-flight + backlog, not to history.

Lease renewal is XCLAIM JUSTID to yourself. A 30-second lease (matching the Postgres lease) with jobs that can run minutes would mean every long job gets stolen by XAUTOCLAIM mid-run. So while a handler runs, the runner heartbeats both stores at LeaseTTL/3: extend the SQL lease (fenced, 4.5), and reset the PEL idle clock — XCLAIM with JUSTID by the current consumer, which resets idle time and changes nothing else. A worker that dies stops heartbeating both, and both clocks agree it's gone.

Poison entries are acked away. An entry whose payload won't decode would otherwise redeliver forever — each claim crashing a worker's decode path, each XAUTOCLAIM finding it again. The fetch path logs it and acks it into oblivion; the job row (if one exists) is caught by the stale-RUNNING sweep instead.

5.4 · The delayed set and the Lua promoter

Streams have no "deliver at time T." Retries with backoff and scheduledAt jobs need one, so delay is a sorted set per priority: ZADD calligraphy:delayed:default <due-ms> <envelope> — member is the encoded envelope, score is its due time. Sorted sets are ordered by score, so "everything due by now" is one ZRANGEBYSCORE key -inf now.

Moving a due member onto its stream takes three commands — read, XADD, ZREM — and the promoter may run on several API replicas while one of them crashes mid-move. Interleave those and members vanish (ZREM before a crash that lost the XADD) or multiply more than necessary. The fix is the standard Redis idiom for multi-step atomicity: a Lua script, because Redis executes a script exactly like one command — nothing interleaves with it:

local due = redis.call('ZRANGEBYSCORE', KEYS[1], '-inf', ARGV[1],
                       'LIMIT', 0, tonumber(ARGV[2]))
for i, member in ipairs(due) do
  redis.call('XADD', KEYS[2], '*', 'j', member)
  redis.call('ZREM', KEYS[1], member)
end
return due

Within the script, XADD-then-ZREM means a crash between the two is impossible; a crash before the script ran leaves the member delayed (retried next tick); the script returns the moved members so the caller can flip their rows RETRYING → PENDING in Postgres. Note the crash after XADD inside a failed script response can still double-deliver — and that's fine, because delivery was at-least-once before the promoter existed (Part XIII).

Leader election, minimum viable. Recovery duties (promote, reap, sweeps — Part XII) run on whichever API replica holds SET calligraphy:leader:recovery <id> NX EX 15 — the classic NX lock with a TTL, renewed at TTL/3, released by a compare-and-delete. The textbook warning about Redis locks (a paused leader's lock expires; two leaders act at once) is real, and the answer here is not a fancier lock but the same move as everywhere else: every duty is idempotent and every write is fenced, so dual leadership costs duplicated effort, never duplicated results. Leadership is an optimization — one process doing housekeeping instead of N colliding — not a correctness requirement. That's why a 15-second lock is enough where a lease on work needed an epoch fence.

The DLQ is a capped stream. Dead-lettered envelopes append to one stream with MAXLEN ~ 10000 (the ~ lets Redis trim lazily at node boundaries, which is cheaper). It's an operator inbox, browsable and re-queueable via API/ctl; the authoritative DEAD_LETTER status lives in the row.

Part VI · gRPC & Protocol Buffers

6.1 · Protobuf: a schema with a wire format

Protocol Buffers are two things wearing one name. First, a schema language: you declare messages and their fields in a .proto file, each field with a type and a number. Second, a binary wire format: an encoded message is just a sequence of (field number, value) pairs — integers as varints (small numbers take one byte), strings and nested messages length-prefixed. Field names never travel; the wire carries 3: 8, and both ends use the schema to know that field 3 of WorkerHello is pid.

Numbers-not-names is what makes protobuf evolvable: a receiver that sees an unknown field number skips it (the wire format is self-delimiting), so adding fields never breaks old readers, and renaming a field is free because the name was never on the wire. The discipline it demands in exchange: never reuse a field number, because the number is the identity. From proto/control.proto:

message WorkerStats {
  int32  active      = 1;
  int32  target      = 2;
  uint64 processed   = 3;
  double utilization = 4;
  bool   paused      = 5;
}

A code generator (protoc with protoc-gen-go) turns the schema into Go structs plus encode/decode — which is why generated .pb.go files are artifacts, not source. During the project rename, a find-and-replace was run across the repo and corrupted the generated files: the old package name was embedded inside a length-prefixed descriptor blob, so changing its bytes without updating the length prefix made the file lie about itself, and every binary panicked at init. The fix — regenerate from the renamed .proto, never edit generated bytes — is Bug 9 in Part XV, and it's a better protobuf lesson than any tutorial: the wire format's length prefixes are load-bearing.

6.2 · gRPC: RPC over HTTP/2, with streams

gRPC is remote procedure calls where the transport is HTTP/2 and the payloads are protobuf. HTTP/2 matters because it multiplexes many independent streams over one TCP connection — so one long-lived connection can carry a call that stays open forever, in both directions, without head-of-line blocking between calls. That enables the four gRPC call shapes: unary (request→response), server-streaming, client-streaming, and bidirectional streaming — both sides send message sequences on one open call, interleaved however they like. The generated code gives each side typed Send/Recv methods; keepalive pings detect a silently dead peer.

6.3 · The control plane, and what it refuses to carry

proto/control.proto · internal/control

Calligraphy uses exactly one RPC, and it's bidirectional:

service Control {
  rpc WorkerStream(stream WorkerMessage) returns (stream Command);
}

Each worker dials the API at boot and holds this stream for its lifetime. Upstream: a WorkerHello (identity, capacity, handled types), then WorkerStats every few seconds, and CommandAcks. Downstream: Drain, Pause, Resume, SetConcurrency{target} — each applied to the pool from Part III (a drain cancels the fetch context; a resize is that one atomic store). The API keeps a hub of connected sessions; the operator reaches it through plain HTTP (POST /api/v1/control/workers/w1/drain), so calligraphyctl stays a dumb HTTP client and the gRPC stream remains a private worker↔API affair.

Why gRPC here at all? The push direction. Worker→API stats could be HTTP POSTs. But API→worker commands over HTTP would mean workers poll for pending commands, and "drain worker 3" would take effect a poll interval later. Over a held-open stream, it takes effect now — sub-second, no polling loop on either side, one connection per worker total. That latency difference is the entire justification, and it's enough: drain-before-deploy is the hot path of operating a fleet.

Decision
Jobs never travel over gRPC — the temptation to "just push work down the stream we already have" is refused, twice over. Work must be durable and claimable: a job pushed over a stream to a worker that dies is a job lost unless you rebuild redelivery, acking, and idle-detection — which is re-implementing Part V's PEL, badly, on a transport that loses everything when the connection drops. The stream carries only ephemeral truth (stats a second stale are harmless; a lost command is re-issued by the operator). Corollary: a worker whose control stream is down keeps processing jobs — the data plane doesn't know the control plane exists.

One bug lived here, worth its cross-reference: when a worker reconnected, the hub evicted the old session by deleting the map entry — but never closed the old stream's send loop, leaking a goroutine per reconnect that occasionally delivered a command to a ghost. The fix gives each session a done channel closed exactly once by an idempotent terminate(); eviction, natural disconnect, and shutdown all converge there (Bug 4, Part XV). The general lesson: in a session registry, removing from the map and ending the session are different operations, and forgetting the second is invisible until you count goroutines.

Part VII · HTTP APIs in Go

7.1 · net/http, and why there's no framework here

Go's standard library ships a production HTTP server. Its model is one interface — Handler: ServeHTTP(ResponseWriter, *Request) — and one router, ServeMux, which since Go 1.22 matches method and path patterns with wildcards natively:

internal/api/server.go
mux.HandleFunc("GET /healthz",  s.handleHealthz)
mux.HandleFunc("GET /readyz",   s.handleReadyz)
mux.Handle("GET /metrics",      s.Meters.Handler())

mux.Handle("POST   /api/v1/jobs",               authed(s.handleSubmit))
mux.Handle("GET    /api/v1/jobs/{id}",          authed(s.handleGetJob))
mux.Handle("GET    /api/v1/jobs/{id}/result",   authed(s.handleGetResult))
mux.Handle("GET    /api/v1/jobs/{id}/attempts", authed(s.handleGetAttempts))
mux.Handle("DELETE /api/v1/jobs/{id}",          authed(s.handleCancel))
mux.Handle("GET    /api/v1/queues/depths",      authed(s.handleDepths))
mux.Handle("GET    /api/v1/dlq",                authed(s.handleListDLQ))
mux.Handle("POST   /api/v1/dlq/{id}/requeue",   authed(s.handleRequeueDLQ))
...
return s.recoverMW(s.logMW(mux))

The server runs one goroutine per connection — Part III's economics are why that's fine at any load this system sees — and each handler reads path parameters with r.PathValue("id"). No chi, no gin, no echo: the standard library now covers method routing and wildcards, which is most of what routers sold, and every dependency in the hot path is a dependency someone must someday upgrade under a CVE. The framework-shaped needs that remain are met the way the stdlib intends — middleware as function wrapping. The last line above is the whole stack: a panic-recovery wrapper outermost (a handler bug becomes a 500 and a log line, never a dead process), request logging inside it, then the mux; authed wraps individual routes with bearer-token checking so health and metrics stay open for probes and Prometheus.

7.2 · The shape of a good JSON API, enforced

Conventions the surface holds to, each for a defendable reason:

Errors are one envelope. Every failure returns {"error":{"code":"…","message":"…"}} with a stable machine-readable code (invalid_json, unknown_type, not_found, payload_too_large…). Clients switch on code; humans read message; nobody parses prose.

Request bodies are bounded. Payloads ride to Redis and back on every delivery, so the API caps bodies with http.MaxBytesReader (256 KB). The subtlety is reporting it: the size limit trips during Decode, so naive code reports "invalid JSON" for a perfectly valid oversized document. The decode path checks errors.As(err, *http.MaxBytesError) first and answers 413 payload_too_large — Bug 5 in Part XV, and a two-line illustration of why error classification deserves tests, not just error presence.

Statuses mean things. Fresh submit → 201. Deduped replay (Part XIII) → 200 with the original job, so the client can even tell which happened. Cancel of an already-terminal job → conflict, not silent success. And submission validates eagerly — unknown job type, malformed payload, bad priority are rejected at the door with a 4xx, because a bad job caught at submit costs one round trip, while the same job caught by a worker costs a claim, an execution, a recorded failure, and an operator's attention.

Timeouts everywhere, shutdown graceful. The server sets read-header/read/write/idle timeouts (a client that sends one byte per minute is an attack, not a user), and SIGTERM triggers http.Server.Shutdown: stop accepting, finish in-flight responses, then exit — the API's small sibling of the worker's two-phase drain.

7.3 · healthz vs readyz — two different questions

func (s *Server) handleReadyz(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 2*time.Second)
    defer cancel()
    if err := s.Store.Ping(ctx); err != nil {
        writeErr(w, http.StatusServiceUnavailable, "not_ready", "database unreachable")
        return
    }
    if err := s.Queue.Ping(ctx); err != nil {
        writeErr(w, http.StatusServiceUnavailable, "not_ready", "redis unreachable")
        return
    }
    writeJSON(w, http.StatusOK, map[string]string{"status": "ready"})
}

/healthz answers "is this process alive?" — it checks nothing external, because the remedy attached to failing it (Part X: restart the pod) fixes nothing about a down database. /readyz answers "can this instance serve a real request right now?" — both dependencies, bounded to 2s so the probe itself can't hang. Conflating them is a classic outage amplifier: put the DB check in liveness and a database blip makes Kubernetes restart every API pod in a loop, turning one failure into two. The remedy for "not ready" is to stop sending traffic, and that's exactly what readiness gates.

Part VIII · Prometheus & Grafana

8.1 · The pull model, and why it's backwards on purpose

Prometheus inverts the arrangement most people expect from monitoring. Applications don't send metrics anywhere; they expose a /metrics endpoint serving a plain-text snapshot of named numbers, and the Prometheus server scrapes every target on an interval (here: 5s), storing each value as a timestamped sample in its time-series database. Pull buys three things: instrumented processes stay trivial (no buffering, no delivery retries, no metrics outage when the collector is down); the scrape itself is a health check (a dead target shows as up == 0 — you learn about death from the absence going somewhere); and one config file lists everything being watched.

A sample is identified by a metric name plus labels — calligraphy_jobs_completed_total{type="demo.sleep"} — and every distinct label combination is its own time series. Labels are the query language's pivot (sum by type, rate per worker), and also the classic self-inflicted wound: a label with unbounded values (job ID, URL) mints unbounded series and eats the server. Calligraphy labels by job type and worker ID — small, fixed sets — never by job.

8.2 · The three instrument types that matter

internal/metrics/metrics.go

A counter only goes up (jobs_submitted_total, jobs_completed_total, jobs_retried_total, writes_fenced_total…). Its absolute value is boring; its slope is the signal, and rate(jobs_completed_total[1m]) is throughput. Counters survive restarts gracefully because rate() detects the reset instead of reporting a negative spike.

A gauge goes both ways (worker_active_jobs, worker_target_concurrency, worker_utilization). The worker exports these as GaugeFuncs reading the pool's atomics directly — the scrape reads the live value, no bookkeeping between.

A histogram answers distribution questions. Internally it is just counters: a set of cumulative buckets (le="0.128" = "observations ≤ 128ms") plus sum and count. Buckets aggregate perfectly across workers (sum the counters), and quantiles are estimated at query time by histogram_quantile(), with error bounded by bucket width — which is why bucket layout is a design decision, not a default to accept. Both duration histograms here use ExponentialBuckets(0.001, 2, 18): 1ms doubling to ~2 minutes, equal relative error everywhere on a scale where jobs legitimately span five orders of magnitude.

8.3 · The one query this system is designed around

Two histograms measure every job: job_duration_seconds (execution: claim to outcome) and job_e2e_duration_seconds (submit to terminal, measured from row timestamps). Neither alone diagnoses anything; their gap is the system's most important derived signal:

histogram_quantile(0.95, sum(rate(calligraphy_job_e2e_duration_seconds_bucket[5m])) by (le))
  -
histogram_quantile(0.95, sum(rate(calligraphy_job_duration_seconds_bucket[5m])) by (le))

That difference is queue wait — time spent owned by the system but not executing. Execution p95 rising means jobs got slower: look at handlers and dependencies. E2E p95 rising while execution holds flat means jobs wait: capacity, not code — add workers or raise concurrency. Part XIV's reliability run shows the signature at full amplitude: execution p50 of 38ms under an e2e p50 of 5.4s — a healthy fleet digesting a burst that arrived nine times faster than it drains. The distinction — slow system vs. saturated system — is the first question in any queue incident, and these two histograms answer it in one glance.

Part IX · Docker: shipping a process

9.1 · What a container actually is

A container is not a virtual machine. There is no guest kernel, no hypervisor, no emulated hardware — a container is an ordinary Linux process that the kernel has been told to lie to, using three mechanisms that predate Docker. Namespaces scope what the process can see: its own PID table (it thinks it's PID 1), its own network stack, its own mount table, its own hostname. Cgroups scope what it can use: memory ceilings, CPU shares — the knobs Kubernetes resource limits turn (Part X). Layered filesystems (overlayfs) give it its own root directory, assembled from stacked read-only layers plus one writable layer on top. Docker's contribution was packaging: the image format that bundles a filesystem with metadata, the registry protocol for moving images, and a UX that made the kernel features usable in one command.

Because a container is just a process, its economics are process economics: starts in milliseconds, no per-VM memory tax, hundreds fit on a laptop. That's what makes "the dev environment is the prod topology" (9.3) reasonable where a VM per service never was.

9.2 · Images, layers, and the two-stage trick

deploy/docker/Dockerfile

An image is a stack of layers, one per Dockerfile instruction, each layer content-addressed and cached: if the instruction and its inputs haven't changed, the layer is reused. Layer thinking explains the first half of the Dockerfile:

FROM golang:1.25-alpine AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download          # its own layer: deps change rarely
COPY . .                     # source changes often -- cache breaks here
ARG BINARY=calligraphy-api
RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/app ./cmd/${BINARY}

Copying go.mod/go.sum before the source means the expensive module download re-runs only when dependencies change; day-to-day builds skip straight to the compile. One parameterized Dockerfile builds all four binaries via --build-arg BINARY=… — four near-identical Dockerfiles would drift apart within a month.

The second half is the part with a philosophy:

FROM scratch
COPY --from=build /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=build /out/app /app
USER 65534:65534
ENTRYPOINT ["/app"]

Multi-stage means the golang toolchain image (~800MB) exists only during the build; what ships is the second stage. And the second stage is FROM scratch — the empty image. This works because Go cross-compiles to a fully static binary: CGO_ENABLED=0 removes the libc dependency, so the binary needs literally nothing else. The runtime image is ~15MB and contains exactly two files: the binary, and CA certificates (the http.callback handler speaks TLS to the outside world and must verify who it's talking to). No shell, no package manager, no libc. The security arithmetic is blunt: a scanner can find no vulnerable packages where there are no packages, and an attacker who somehow gains code execution finds no /bin/sh to spawn. USER 65534 is numeric because scratch has no /etc/passwd to resolve a name in — and it means even that hypothetical attacker isn't root.

Two deliberate absences: no tzdata (everything in Calligraphy is UTC, enforced at the edges) and no wget/curl — which has an operational consequence taken with eyes open: nothing inside the container can run a healthcheck. Kubernetes doesn't care (its httpGet probes originate from the kubelet, outside the container — Part X); compose gates startup on Postgres/Redis health instead, and the binaries retry their dependencies at boot anyway (4.7's any-order migrator is part of the same posture).

Part X · Kubernetes: running a fleet

10.1 · The idea: desired state, reconciled forever

Kubernetes inverts imperative operations the way Prometheus inverts metrics delivery. You never tell it "start a worker"; you write into its API "there exist 3 worker replicas," and controllers run reconciliation loops that compare desired state to observed state and act on the difference, forever. Kill a pod and the ReplicaSet controller notices 3 ≠ 2 and starts another; drain a node and its pods reappear elsewhere. The chain for a stateless app: a Deployment (desired template + replica count, plus rollout strategy) manages ReplicaSets (one per template revision) manage Pods (one or more containers sharing a network namespace — the unit that actually runs). A Service gives a stable virtual IP/DNS name that load-balances across whatever pods currently match its selector, because pod IPs are ephemeral by design.

The reason this maps so cleanly onto Calligraphy: the system was already built for members dying and appearing at any moment — that's Parts IV, V, and XII. Kubernetes churn (rollouts, evictions, node failures) is just the crash-recovery story happening on a schedule. The manifests in deploy/k8s/ are namespace, config, Postgres and Redis (dev-grade, single-replica), the API Deployment + Service, the worker Deployment, and an HPA.

10.2 · Probes: wiring Part VII into the platform

deploy/k8s/api.yaml · deploy/k8s/worker.yaml
livenessProbe:
  httpGet: { path: /healthz, port: http }
  periodSeconds: 10
readinessProbe:
  httpGet: { path: /readyz, port: http }
  periodSeconds: 5

Liveness failing → kubelet restarts the container ("process wedged; turn it off and on"). Readiness failing → the Service stops routing to this pod, without restarting it ("alive but can't serve — usually a dependency; wait"). The API declares both, pointing at Part VII's two endpoints, and the split earns its keep in exactly the scenario 7.3 warned about: Postgres blips, every API pod goes not-ready, traffic stops, Postgres returns, pods go ready — zero restarts, no crash-loop amplifying a database problem into an application outage. The workers declare only liveness (on the metrics port): they receive no traffic, so readiness would gate nothing — their version of "ready" is claiming jobs, which the queue itself load-balances. And httpGet probes are why the scratch image (9.2) gets away with having no shell: the kubelet makes the HTTP call from outside; an exec-style probe would have nothing to execute.

10.3 · Shutdown, with a deadline that must out-wait the drain

# worker.yaml
terminationGracePeriodSeconds: 40   # DrainTimeout is 25s; 40 > 25 + margin

Pod termination is a fixed ritual: the pod is removed from Service endpoints, PID 1 receives SIGTERM, and after terminationGracePeriodSeconds whatever remains receives uncatchable SIGKILL. The worker's SIGTERM handler is Part III's two-phase drain, which needs up to 25s of phase one plus a short phase two — so the grace period is 40. Get that inequality backwards (grace < drain) and every routine deploy SIGKILLs mid-flight jobs, silently converting rollouts into the crash path. The crash path works — that's Part XII's whole point, and the reliability run proves it — but it costs lease-expiry latency on the affected jobs, and paying it on purpose, on every deploy, is an unforced error. Rollouts here are: new pod starts → probes pass → old pod drains gracefully → repeat. Jobs never notice.

10.4 · Two autoscalers, two different questions

deploy/k8s/hpa.yaml · internal/scale
minReplicas: 2
maxReplicas: 12
metrics:
- resource: { name: cpu, target: { averageUtilization: 75 } }

The HorizontalPodAutoscaler adjusts the worker replica count to hold average CPU near 75%. CPU is the honest choice for the metric actually available out of the box, and for CPU-bound handlers it's correct. But Part XIV's data shows why CPU is the wrong signal for I/O-bound fleets: an I/O-heavy worker can be drowning in queued jobs at 8% CPU. The right external signal would be queue depth (via an adapter feeding custom metrics to the HPA — noted in the manifests as the production upgrade path). Meanwhile, inside each worker, Calligraphy's own autoscaler answers the other scaling question: not "how many pods" but "how much concurrency per pod" — nudging the pool target (Part III) up when the queue is deep and utilization is high, down when idle, within [MinConcurrency, MaxConcurrency]. The two compose because they operate on different variables at different speeds: concurrency moves in seconds and is free; replicas move in tens of seconds and cost nodes.

11.1 · The happy path, end to end

Order matters in two places, and both are load-bearing. At submission, INSERT before XADD: the row is the job's birth certificate, so a crash between the two leaves a job that exists but isn't moving — repairable (Part XII), whereas the other order leaves a moving job that doesn't exist, which is a delivery with no truth to update. At completion, record before ack: a crash between the two leaves a completed job still claimable — the redelivery loses the claim arbitration or gets fenced, costing a duplicate execution at worst. The other order (ack, then crash before record) loses the outcome entirely with nothing left in Redis to redeliver: that's the one window the DB-side sweep exists for.

11.2 · The runner's outcome routing

11.3 · The state machine is an allow-list

internal/job/statemachine.go
PENDING ────────► RUNNING          claim won
PENDING ────────► CANCELLED        cancelled before any claim
RUNNING ────────► COMPLETED | RETRYING | FAILED | DEAD_LETTER | CANCELLED
RETRYING ───────► PENDING          backoff elapsed; promoter moved it
RETRYING ───────► RUNNING          a live redelivery claimed it first
RETRYING ───────► CANCELLED
DEAD_LETTER ────► PENDING          operator requeue
COMPLETED / FAILED / CANCELLED     no exits. Terminal means terminal.

Every transition in the codebase goes through this table; anything not listed is an error, and the tests enumerate all 49 (from, to) pairs and assert each one's verdict. The odd-looking edge is RETRYING → RUNNING, which seems to skip PENDING: it exists because under at-least-once delivery a retrying job can legitimately still have a second stream entry in flight (a repair re-enqueue racing the original), and the claim UPDATE accepts status IN ('PENDING','RETRYING') precisely so whichever delivery arrives first wins. An honest state machine names the edges reality uses, rather than modeling the world you wish you had.

Part XII · Failure is the design

12.1 · Naming the windows instead of hoping

Part II admitted the cost of two stores: every operation that writes both can crash between the writes. The design response is to refuse vagueness — enumerate every window, and pair each with a repair duty that (a) detects it from durable state alone and (b) is safe to run even when nothing is wrong. There are four:

#WindowWhat's left behindRepair
1Submit: INSERT committed, XADD never happened PENDING row, no stream entry — a job that exists but will never be fetchedrepairUnenqueued: find PENDING rows past an age with no confirmed enqueue; re-XADD from the row itself
2Retry: row flipped RETRYING, ZADD to the delayed set lostRETRYING row whose promotion never comes repairStuckRetrying: RETRYING rows whose scheduled_at is long past — re-park or re-enqueue
3Worker dies mid-run (SIGKILL, OOM, node loss) RUNNING row + PEL entry, both with ticking clocks and a consumer that will never ackthe reaper: XAUTOCLAIM past min-idle finds the entry (5.2); the row's lease expiry agrees; epoch is bumped (revoking the zombie, 4.5) and the job is re-enqueued
4Completion: acked, then crashed before the record landedRUNNING row with no PEL entry anywhere — Redis has forgotten the job while Postgres thinks it's running sweepStaleRunning: RUNNING rows whose lease is long expired and which the reaper can't see; re-enqueued from the row

Plus one bookkeeping duty (mark heartbeat-silent workers gone) and the promoter itself (5.4), which is less a repair than the scheduled half of the retry mechanism. All of it runs on whichever API replica holds the leader lock — and per 5.4, leadership is an optimization: every duty is conditional-UPDATE-guarded, fenced, and idempotent, so two leaders in a handover moment duplicate effort, not results.

12.2 · The deliberate redundancy

Windows 3 and 4 overlap on purpose: the reaper watches from Redis's side (PEL idle time), the sweep from Postgres's side (lease expiry, no PEL entry). Either alone almost covers worker death; together they cover it from both directions, and the sweep additionally catches window 4, which the reaper structurally cannot see (there is no PEL entry left to claim). When both fire on the same job — reaper first, sweep later — the second finds a row whose status and epoch already moved on, matches zero rows, and does nothing. Idempotency is what lets you afford overlapping safety nets; without it, redundancy would be a bug generator.

12.3 · What the reliability run actually proved

The claim "crash-safe" is tested, not asserted: 10,000 jobs with 5% injected transient failures and ~1% injected permanent failures, and two workers SIGKILLed mid-load (no drain, no goodbye — the kill the design is for). Eight jobs were in-flight on the murdered workers; all eight were reaped (lease_expired attempts in their history) and completed on survivors. The attempt ledger balances: 10,485 attempts = 10,000 first tries + 485 retries. That last number is the audit that matters — "nothing lost" is provable only because every attempt leaves a row (ON CONFLICT (job_id, attempt) DO NOTHING, so even repair re-records collapse into one truth).

Part XIII · Retries & idempotency

13.1 · Why at-least-once isn't a choice

A worker executes a job, then tells the system it's done. Those are two events with a gap between them, and the process can die in the gap. When it does, the system holds an executed-but-unacknowledged job and faces a binary decision with no third option: deliver it again (risking a duplicate execution) or don't (risking a lost job). That's the whole theorem, and no protocol sophistication escapes it — acknowledging the acknowledgment just moves the gap. Calligraphy chooses redelivery — at-least-once — because a duplicate is a nuisance you can engineer away one layer up, while a loss is invisible and unrecoverable by definition. Every mechanism in this document that smelled redundant — arbitration (4.4), fencing (4.5), the RETRYING → RUNNING edge (11.3), idempotent repairs (12.2) — is the system being honest about that choice.

What about "exactly-once," which several commercial queues print on the box? Read their fine print and it's at-least-once delivery plus deduplication at a boundary — which is real and useful and not exactly-once execution of arbitrary side effects. Calligraphy's claim is deliberately precise: at-least-once execution, exactly-once result persistence (the fence guarantees at most one attempt's write wins), and duplicate-safe submission (13.4). Side effects inside handlers are the handler author's contract, stated next.

13.2 · The retry policy, and its shape under a real outage

internal/retry/backoff.go
delay = uniform(0, min(cap, base · 2^(attempt−1)))     // "full jitter"

Exponential growth is the uncontroversial half: consecutive failures usually mean a struggling dependency, so attempts spread out — base 2s doubling toward a 5-minute cap (both configurable). The jitter choice is the interesting half. Deterministic exponential backoff has a herd problem: 500 jobs failing against one downed service in the same second retry in the same later second, in lockstep, forever — each synchronized wave landing on a dependency mid-recovery. Full jitter draws uniformly from [0, ceiling], spreading each wave across its whole window; AWS's published measurements found it best among the variants for both total load and time-to-completion. The cost — some retries fire near zero delay — is acceptable: against a blip they succeed; against an outage they spend one attempt whose successor draws from a window twice as wide. One deliberate exception: interrupted outcomes (worker shutdown, 11.2) retry with near-zero backoff, because the job did nothing wrong.

Attempts are bounded (maxAttempts, default 5, counted at claim — 4.4), and exhaustion routes to the DLQ: status DEAD_LETTER in Postgres, envelope appended to the capped DLQ stream (5.4) as an operator inbox. Requeueing (API or ctl) resets attempt_count to 0 and bumps the epoch — a fresh budget, because an operator requeues after fixing the cause, and a jail you can't leave isn't an inbox.

13.3 · Idempotency: the handler's half of the contract

The platform guarantees attempts ≥ 1; the handler must make attempts > 1 harmless. That property is idempotency — f(f(x)) = f(x) — and it's a per-handler design obligation, not a library you import. The built-in handlers model the three standard techniques:

Natural idempotency. article.analysis computes a summary and writes it keyed by article ID. Running it twice writes the same value twice — the operation is idempotent because "set X to V" is, and where you can shape work into that form, do nothing further.

Dedupe material for the receiver. http.callback can't make someone else's server idempotent, so it forwards the means: every delivery carries X-Calligraphy-Job-Id and X-Calligraphy-Attempt, and is signed — X-Calligraphy-Signature: v1=HMAC-SHA256(secret, timestamp‖body) with the timestamp echoed in a header, so the receiver can verify authenticity, reject stale replays, and deduplicate on job ID. That's the webhook idiom used by Stripe et al., and it turns "my endpoint got called twice" from a platform bug into a receiver checkbox.

Fencing, when only one writer may win. For effects that must land at most once and live where you control the schema, the pattern is 4.5's: a token checked in the write predicate. The platform applies it to its own result writes; handlers with similar needs (e.g. "apply this payment") should carry the job ID into the target table's unique key and let the database refuse the duplicate.

13.4 · Submission dedupe closes the loop

The client is a distributed-systems participant too: its POST can time out after the INSERT landed, and its retry would mint a second job — duplicate work, invisible to per-execution idempotency. Hence idempotencyKey: the partial unique index (4.7) makes (type, key) collide, ON CONFLICT DO NOTHING makes the collision silent, and the API returns the original job with 200 (vs 201 fresh). The TS client generates keys automatically for Booklet's submissions. End to end, every hop is now duplicate-safe: client→API by idempotency key, API→queue by windows 1–2's repairs being conditional, queue→worker by claim arbitration, worker→truth by the fence.

14.1 · Methodology, and what a number is allowed to mean

Part XV · A history of mistakes

Every bug below is real: found during this build, diagnosed, fixed, and in most cases converted into a regression test. They are the most honest teaching material in this document — each one is a place where a correct-sounding mental model met the machine and lost. Kept in the order they were found.

Bug 1 · The outcome that could never happen
The taxonomy defined OutcomePanicked; the runner recovered panics and converted them to errors — which the classifier then labeled generic retryable. The panicked outcome existed in the enum and was unreachable in practice, so panicking handlers were indistinguishable from flaky networks in every attempt record. Fix: the recover path wraps the panic in a marker error the classifier detects, so panics route as retryable and record as what they are. Lesson: an enum arm nothing produces is a claim your tests aren't checking; assert the routing, not just the recovery.
Bug 2 · Asking the wrong context why it died
Cancelled jobs were ending up RETRYING instead of CANCELLED. The runner read context.Cause(poolCtx) — the pool's context — but the cancel flag cancels the per-job execution context; the pool context was alive and well, so the cause read as nil and classification fell through to "transient". Fix: capture context.Cause(execCtx) before cleanup tears the context down, and classify from that. Lesson: in a tree of contexts, "why was I cancelled" must be asked of the context that was actually cancelled — parents don't know what happened to their children.
Bug 3 · json.Unmarshal merges; it does not replace
The bench's drain-detection loop decoded queue-depth responses into a reused struct. encoding/json merges into existing maps rather than clearing them, so a priority whose count fell to zero — and therefore stopped appearing in the response — kept its stale nonzero value forever, and the harness reported jobs stuck at PENDING that had completed minutes earlier. Fix: fresh struct per poll. Lesson: decoder reuse semantics are real API surface; and verification code is code — a false "it's broken" costs the same hours as a true one.
Bug 4 · Removed from the map, alive on the wire
When a worker reconnected to the control plane, the hub evicted the old session by deleting its map entry — but the old stream's send goroutine kept running, occasionally delivering a command to a connection nobody owned. Fix: sessions carry a done channel closed exactly once by an idempotent terminate(); eviction, disconnect, and shutdown all converge on it. Lesson: in a session registry, forgetting an object and ending its lifecycle are different operations; conflating them leaks goroutines you only notice when you count them.
Bug 5 · The 413 that reported as 400
Oversized submissions returned 400 invalid_json. The body cap (http.MaxBytesReader) trips during JSON decoding, so the decode error path swallowed it. Fix: check errors.As(err, *http.MaxBytesError) before concluding "malformed" and answer 413 payload_too_large. Lesson: at API boundaries, test error classification, not just error presence — a wrong code sends a client debugging their JSON when their JSON is fine.
Bug 6 · jsonb stores values, not bytes
Submission dedupe verified that a replayed idempotency key carried the same payload by comparing stored bytes to incoming bytes. Postgres jsonb canonicalizes — key order, whitespace, number forms — so equal payloads compared unequal depending on how the client serialized. Fix: decode both and compare semantically. Lesson: jsonb's parse-on-write is a feature (indexing, containment) with a contract: you stored a value, so don't expect your bytes back.
Bug 7 · The test that tested a different pipeline
A DLQ test enqueued, forced failures, then counted DLQ entries — but read the stream directly instead of consuming through the group like a worker does, and counted an entry that the real path would have claimed. The test passed against broken behavior. Fix: the test consumes its delivery exactly as a worker would. Lesson: a test that shortcuts the pipeline verifies the shortcut; fidelity to the real read path is what makes an integration test integrate.
Bug 8 · 9 + 9/2 is 13 here
An autoscaler test expected a midpoint of 14 from values the code computes as 9 + 9/2 — which in Go's integer arithmetic is 9 + 4 = 13. The code was right; the test author's mental floating point was wrong. Fix: the test. Lesson: when a test disagrees with the code, re-derive the expectation using the machine's arithmetic, not yours — and only then decide which side is the bug.
Bug 9 · sed vs the wire format
The project rename (Forge → Calligraphy) was applied by find-and-replace across the repo — including generated .pb.go files, where the old name lived inside a length-prefixed protobuf descriptor blob. Changing the bytes without updating the prefix made the descriptor lie about its own length, and every binary panicked at init with slice bounds out of range. Fix: rename the .proto, regenerate with protoc, never edit generated bytes. Lesson: generated files are build artifacts wearing source-file clothing; and length-prefixed formats are load-bearing in a way plain text never is (6.1).
Bug 10 · go test runs packages in parallel
After the rename, integration tests started failing with jobs "stuck at PENDING" — but only sometimes, and never alone. Cause: each integration package flushes the shared Redis/Postgres in its setup, and go test ./... runs packages concurrently by default, so one package's flush wiped another's in-flight state mid-test. Fix: -p 1 for the integration suite (unit tests stay parallel). Lesson: test parallelism across packages is a default you opted into without noticing; shared external state demands either serialization or per-package namespacing, and "flaky" usually means "concurrent".

A meta-lesson from the set: five of the ten (1, 2, 3, 7, 8) are bugs in testing and verification machinery, not in the system proper. That ratio isn't embarrassing, it's the point — the verification layer is held to the same standard as the code, because a test that lies is worse than no test at all.

Part XVI · Glossary, in plain words

Every term this document leans on, defined without circularity. When a definition depends on another entry, the dependency is a real arrow — read the glossary as a tiny course.

TermPlainly
ack (acknowledge)The consumer telling the queue "this delivery is finished; stop tracking it." Until then the queue assumes the work may need redelivering.
advisory lockA Postgres lock on a number you invent, enforced only among cooperating callers. Used to make N simultaneous migrators take turns.
at-least-onceThe delivery promise "nothing is lost, but duplicates can happen." The forced choice once acknowledgments can be lost; its complement is at-most-once ("no duplicates, but loss can happen").
backpressureA full system slowing its intake instead of absorbing unbounded work into memory. Here: the pool fetches only its free capacity, so backlog stays in Redis.
bounded poolA worker design where at most N jobs run concurrently because the code structurally cannot start an (N+1)th.
claimWinning the right to execute a delivery — here, a conditional UPDATE where "1 row affected" means you won.
consumer groupRedis Streams machinery that lets many consumers share one stream, each entry handed to exactly one of them, with per-entry pending bookkeeping.
contextGo's cancellation carrier: a value passed down call chains whose "done" signal tells everything beneath it to stop.
dead-letter queue (DLQ)Where jobs go after exhausting retries: out of the traffic, in front of a human, requeueable after the cause is fixed.
deliveryOne handing of a job to a worker. One job can have many deliveries (redeliveries); each is a fresh attempt at a claim.
drainGraceful shutdown for workers: stop taking new work, finish what's running, then exit.
envelopeThe small encoded record that travels through Redis: job ID, type, priority, attempt — the pointer to the truth, not the truth.
fencing token / epochA number that grows each time ownership of a resource changes, checked on every write so a stale owner's writes land as no-ops. The cure for zombies.
fsyncThe system call that forces written data to physical storage. Durability's price tag; commits pay it.
full jitterRetry delay drawn uniformly from [0, ceiling] where the ceiling doubles per attempt — exponential backoff that also decorrelates a herd of failures.
goroutineGo's cheap concurrent function: kilobytes of stack, scheduled in user space, so "one per job" is a design, not a crime.
heartbeatA periodic "still alive, still working" signal. Its absence is how the system detects death without anyone reporting it.
histogram (Prometheus)A distribution recorded as cumulative bucket counters, aggregatable across processes; quantiles are estimated from it at query time.
HPAKubernetes' HorizontalPodAutoscaler: a control loop that adjusts replica count to hold a metric near a target.
idempotencyThe property that doing something twice equals doing it once. What handlers must provide so at-least-once delivery is safe end to end.
idempotency keyA client-chosen string that makes resubmitting the same logical work return the original job instead of minting a twin.
leaseTime-bounded ownership: a claim that expires unless renewed, so a dead owner's work becomes reclaimable automatically.
leader electionPicking one process (here: via an expiring Redis lock) to do housekeeping so N replicas don't collide doing it N times.
liveness / readinessKubernetes' two health questions: "should I restart this?" vs "should I send this traffic?" Different remedies, so different probes.
MVCCMulti-version concurrency control: writers create new row versions instead of overwriting, so readers never block writers.
PEL (pending entries list)A consumer group's ledger of delivered-but-unacked entries, each with owner and idle time. The queue's crash detector.
poison messageAn entry that can never be processed (e.g. undecodable) and would redeliver forever if not removed on sight.
promoterThe loop that atomically moves due delayed jobs (retries, scheduled work) from the sorted set back onto their stream.
protobufA schema language plus compact binary encoding where fields travel as numbers, making messages small and safely evolvable.
quantile / p95The value below which 95% of observations fall. Tail latency; the number users feel and averages hide.
reaperThe recovery duty that reclaims work from consumers gone silent past their lease, using the PEL's idle clocks.
scrapePrometheus fetching a target's /metrics snapshot on an interval. Monitoring by pulling, not pushing.
SIGTERM / SIGKILLThe polite and impolite kill signals: one is catchable and starts a drain; the other ends the process mid-thought — which recovery must survive.
state machineAn explicit allow-list of (from, to) status transitions where everything absent is an error, not an option.
stream (Redis)An append-only log of ID-stamped entries inside Redis; with consumer groups, a work queue with delivery bookkeeping.
visibility timeoutQueue-speak for "claimed work returns to the pool if not finished in time" — implemented here by PEL idle time plus XAUTOCLAIM.
WAL (write-ahead log)The sequential log a database flushes before touching data files, making one fsync stand for a whole commit.
zombieA process acting on ownership it lost — paused, partitioned, or slow — whose writes fencing turns into no-ops.
ZSET (sorted set)A Redis structure ordering members by score. Score = due-time turns it into a time-indexed parking lot for delayed work.

That is the whole system: a bounded pool fed by streams, arbitrated and fenced by a relational truth store, repaired by idempotent sweeps, measured by two histograms and their gap, shipped as 15MB of static binary, and documented — bugs, regressions, and dead ends included — the way it was actually built. If you read straight through: you now know what a PEL is, why zero rows affected is an answer, and what it costs to find out that batching wasn't the bottleneck. That was the point.
