Forge: The Complete Technical Documentation

How a distributed job platform works when you assume every worker will eventually die mid-job — and what building one teaches you. Covers not just the design but the bugs, the measurements that contradicted the plan, and the trade-offs written down while they were being made.
Go 1.25 · PostgreSQL 16 · Redis 7 · gRPC · Prometheus · Docker · Kubernetes — v1, August 2026

Part 0 · How to read this document

This is the long-form companion to the README. The README advertises; this explains. It is written to be readable by someone who has never built a queue, in order, but every part stands alone if you arrive from a link.

Three kinds of callout appear throughout:

Decision
A choice that could have gone another way, with the reasoning recorded at the moment it was made — so a future reader argues with the reasoning, not a guess about it.
Trade-off
Something given up on purpose. Every real system is a pile of these; the dishonest ones just don't label them.
Bug — found and fixed
A real defect from this project's history, kept because the mistake teaches more than the fix. Part 10 collects all of them.

Part 1 · Why Forge exists

Forge was built as the asynchronous tier for Booklet, a read-it-later platform. Booklet's own source comments document four places where background work is either blocking a user or quietly droppable:

WhereBooklet's own words / behavior
Article extractionRuns on the save request: up to a 15-second page fetch, Readability parsing, and as many as 30 image downloads while the user watches a spinner. A failure is recorded and the work is simply gone.
Embedding indexingA fire-and-forget promise: "failures are logged and dropped… a backfill script re-attempts anything missed." The recovery plan is a human remembering to run a script.
Webhook delivery"At-least-once, no retry queue yet — a receiving endpoint being briefly down loses that one delivery." (As written it is actually at-most-once.)
Feed polling"There's no background worker in this app to poll feeds on a schedule."

Four features, one missing piece of infrastructure: somewhere to put work that must happen, must survive a crash, may fail transiently, and must never make a user wait. That is the entire product definition of Forge — and the reason it is a separate service with a public API rather than a Booklet module. Infrastructure that imports your product's code isn't infrastructure; it's a big product.

Decision
Forge contains none of Booklet's business logic and never touches Booklet's database. For work whose logic must stay in Booklet (extraction needs Readability), Forge holds the schedule, retries, and dead-letter queue, and calls Booklet back over signed HTTP — the Cloud Tasks model. That's what keeps Forge reusable by any application.

Part 2 · The shape of the system

The whole architecture fits in three sentences, and everything else in this document is a footnote to them:

Redis moves the work. Jobs travel as self-contained envelopes through Redis Streams, so dispatching work never requires a database read. Redis is fast, and it is allowed to be merely fast because it is not the record.

Postgres records the truth. Every job, every attempt, every state change lives in four tables, forever. When Redis and Postgres disagree — and in crash windows they briefly can — Postgres wins, and three repair sweeps exist to make it so.

gRPC carries only control. Worker stats stream up; drain/pause/resize commands stream down. Jobs never travel there — a control channel that grows job-delivery ambitions becomes a second, worse queue.

Why a stream and a database, not one or the other

A queue alone can't answer "what happened to job X yesterday" — that's a SQL question. A database alone makes a poor queue — polling a table for work means either hammering it or adding latency, and row locks under concurrent claimants get ugly. Using each for what it's good at costs one real thing: seams. Every operation that writes to both (submit = INSERT + XADD; retry = UPDATE + ZADD) can crash between the two writes. Forge's answer is to make each seam's failure detectable and repairable (Part 4) rather than pretending atomicity across two systems.

Trade-off
Two stores means two things to operate and a class of repair machinery a single-store design wouldn't need. The alternative — Postgres-only with SELECT … FOR UPDATE SKIP LOCKED — is a legitimate design at small scale and would have been simpler. Streams were chosen because the consumer-group machinery (per-message acks, idle-time reclaim) solves the crashed-worker problem natively, and because the target deployment already operates Redis.

Part 3 · The life of a job

A job is born over HTTP (POST /api/v1/jobs), becomes a row (durable) and an envelope (in motion), gets claimed by exactly one worker at a time, and ends in one of four terminal states. The state machine is an explicit allow-list — a literal Go map of legal edges — and every one of the 49 possible (from, to) pairs is tested, the illegal ones as thoroughly as the legal ones.

PENDING ──► RUNNING ──► COMPLETED
   │            ├──────► FAILED        (handler said: permanent)
   │            ├──────► RETRYING ──► PENDING   (backoff elapsed)
   │            ├──────► DEAD_LETTER   (attempts exhausted)
   │            └──────► CANCELLED     (cooperative)
   └──► CANCELLED                      DEAD_LETTER ──► PENDING (operator)

Claim arbitration: the database as referee

Under at-least-once delivery, the same job can legitimately have two stream entries in flight (a redelivery, a repair sweep re-enqueueing something whose first enqueue's receipt was lost). Which worker wins? The claim is a conditional UPDATE:

UPDATE jobs SET status='RUNNING', lease_epoch = lease_epoch + 1, …
WHERE id = $1 AND status IN ('PENDING','RETRYING')

Whoever's UPDATE matches first wins. Everyone else matches zero rows, which is not an error — it's the database saying someone else got here first — and the losing delivery is simply acknowledged away. One idea, used everywhere: races are resolved by conditional writes, and "zero rows affected" is a signal, not a failure.

Decision
attempt_count increments at claim time, not at completion. A worker that dies mid-attempt has still consumed an attempt. Counting at completion undercounts crashes — which are precisely the failures retry budgets exist to bound.

The one ordering rule

When a job finishes, two things must happen: its outcome becomes durable in Postgres, and its stream entry is acknowledged in Redis. The order is fixed, everywhere, forever: record first, ack second. Crash between them and the job re-runs (annoying, promised by at-least-once, handled by idempotency). Reverse the order and a crash between them loses the job — acknowledged in Redis, never recorded, invisible. One of those failure modes is a shrug and the other is the worst thing a job system can do.

Part 4 · Failure is the design

The scenario every queue must answer without hand-waving: a worker claims a job and dies — SIGKILL, OOM, kernel panic, unplugged. No goodbye, no ack. Postgres says RUNNING. Now what?

Leases: permission to be trusted, with an expiry

A claim is not ownership; it's a lease. While a handler genuinely runs, its worker renews the lease every TTL/3 — in Redis by resetting the stream entry's idle clock (XCLAIM JUSTID), in Postgres by extending lease_expires_at. A healthy long-running job renews forever. A dead worker stops renewing, and the silence is the signal.

Decision
The lease TTL is sized to crash-detection latency, never to job duration. Long jobs don't need long leases — they need heartbeats. This is what lets a 10-second TTL coexist with a 10-minute job: the job renews 30 times, and a crash is still detected within ~10 seconds.

The reaper, and the zombie it must expect

A leader-elected loop asks Redis for entries whose consumer has been idle past the lease (XAUTOCLAIM — the visibility timeout, built into the data type). For each, the database decides: attempts left → RETRYING with backoff; exhausted → DEAD_LETTER. Either way, one more thing happens in that UPDATE: lease_epoch = lease_epoch + 1.

That increment is the fencing token, and it exists for the worker that wasn't dead — just stalled (GC pause, CPU starvation, network partition) — and wakes up after its job was given away, still holding a result it wants to write. Its write carries the epoch it was issued at claim time:

UPDATE jobs SET status='COMPLETED', result=$3, …
WHERE id = $1 AND lease_epoch = $2 AND status='RUNNING'

The row's epoch has moved on. Zero rows match. The zombie's write lands on nothing, it logs, it moves on. The job may execute twice; its result is written exactly once. No amount of wall-clock lease tuning achieves this — the zombie doesn't know it's a zombie — only the token does.

The crash windows, enumerated

Every two-store operation has a seam. Forge's posture is to name each one and assign it a repair mechanism, because "we assume that doesn't happen" is how jobs vanish:

WindowSymptomRepair
Submit: INSERT landed, XADD didn'tPENDING row, no delivery everOrphan sweep: rows past 30s with no enqueue receipt are re-enqueued. If the XADD actually succeeded and only its receipt was lost, the duplicate delivery collapses at claim arbitration.
Retry: UPDATE landed, ZADD didn'tRETRYING row waiting for a promotion that will never comeStuck-retry sweep: overdue RETRYING rows are enqueued directly, skipping the long-passed backoff.
Crash mid-runSilent PEL entry, expired lease The reaper (above), on the PEL's own idle clock.
Crash between ack and record flushRUNNING row, no PEL entry leftDB-side sweep: long-expired RUNNING rows are reaped from the row itself (the envelope is rebuilt from the columns — which is why the sweep query returns full rows, not bare ids).
Decision
Leadership (a Redis lock) gates these duties as an optimization, not a correctness requirement. Every duty is idempotent and fenced, so a split-brain moment during lock handover duplicates effort, never results. Recovery that requires a perfect leader election has just moved the hard problem, not solved it.

Proof by kill -9

All of the above is enforced by a test that does the actual thing: re-execute the test binary as a real child worker process, wait until it has provably claimed a job and begun executing, SIGKILL it, start the reaper and a healthy worker, and assert the job completes with the attempt history reading lease_expired (doomed-worker) → completed (healthy-worker). It runs in CI on every push, and the same mechanism was exercised at scale in the 10,000-job benchmark: two workers killed mid-run, 8 in-flight jobs reaped, all 8 completed.

Part 5 · Retries & idempotency

Full jitter, because retries synchronize

When a dependency blips, hundreds of jobs fail in the same second. Fixed backoff retries all of them at the same instant, forever, in lockstep — each wave landing on a dependency that's trying to recover. Forge draws each delay uniformly from [0, min(cap, base·2^(attempt−1))) — "full jitter", the variant AWS's published measurements found best for both server load and completion time. The retry storm becomes retry drizzle.

Not all failures deserve a retry

Handlers classify: an unmarked error retries (the default leans toward the recoverable mistake — wrongly retrying a permanent failure wastes attempts and surfaces in the DLQ where a human sees it; wrongly dropping a transient one silently loses work). NonRetryable(err) routes straight to FAILED — retrying a malformed payload five times is just five identical failures. HTTP callbacks map status codes: 5xx/408/429 retry, other 4xx are permanent, redirects are refused outright (replaying a signed POST to a redirect target would vouch for a body to a host nobody registered).

What Forge guarantees, and what it refuses to claim

GuaranteedExplicitly not claimed
• At-least-once execution
• Exactly-once result persistence (fencing)
• Idempotent submission: same (type, key) → the original job, ever after
• Every job terminal or visibly stuck; none silently lost 		• Exactly-once execution — no queue can promise this from outside the handler, and docs claiming it are hiding a dedup layer. If a handler emails someone and dies before acking, the email went out and the job will run again. Only an idempotent handler fixes that, which is why the handler contract says so in bold.
Trade-off
The 10k benchmark retried 485 jobs — at-least-once means at least. The system's honesty budget is spent making duplicates safe (fencing, idempotency keys, per-attempt coordinates handlers can dedupe on) rather than pretending they don't occur.

Part 6 · The worker runtime

The pool is the limiter

The fetch loop computes free = target − active before every fetch and never asks Redis for more. That single line is the concurrency bound and the backpressure mechanism: there is no internal buffer channel, so claimed-but-unstarted work cannot pile up invisibly inside a process. Backlog stays in Redis — visible in queue depth, durable, claimable by any worker with capacity. Resizing is an atomic store the loop re-reads each iteration; shrinking just stops fetching until enough jobs drain.

Decision
No go handle(msg) per message, ever. Unbounded goroutines mean memory and scheduler pressure scale with queue depth — the busiest moment becomes the moment the worker falls over. The bound is structural: the loop cannot create more than target goroutines because the loop is the only thing that creates them.

Graceful drain, and the honest limits of grace

SIGTERM stops fetching; in-flight jobs get DrainTimeout to finish on their own; then their contexts cancel (handlers see it; well-behaved ones return promptly); a short grace later, anything still running is abandoned to the reaper — which is fine, because surviving ungraceful death is the whole Part 4. Grace is an optimization that saves a retry, not a correctness requirement.

Panics are attempts, not funerals

A panicking handler is caught, its stack preserved in the attempt row, and the attempt classified panicked (retryable — if it panics every time, the attempt budget routes it to the DLQ where the stack is waiting). One bad payload must not take down a worker running seven other jobs.

The built-in handlers

HandlerWhat it's for

Part 7 · Observing & operating it

The metric that matters most is a gap

Forge records two duration histograms per job type: execution time (inside the handler) and end-to-end time (enqueue → done). Their p95s plotted together are the dashboard's most useful panel, because the distance between the lines is time spent waiting, not working. Execution flat while e2e climbs means you need capacity, not faster handlers — backpressure drawn as two lines.

The control plane, and why gRPC is confined to it

Each worker holds one bidirectional stream open to the API: stats up every 5 seconds, commands (drain / pause / resume / set-concurrency) down the moment an operator issues them. Push is what earns gRPC its place — "drain worker 3 now" over polled HTTP waits out a poll interval. The boundary is strict: jobs never travel here, and a worker that loses the control plane keeps processing jobs indefinitely (it reconnects with backoff; losing control costs operability, never throughput).

Scaling: two composable axes

Each worker can autoscale its own concurrency from queue depth — grow eagerly (+half per interval when backlog ≥ 2× capacity), shrink reluctantly (five consecutive idle observations, −1 at a time), and one subtlety with its own test: a busy pool with an empty queue is not idle — it's working at exactly capacity, and shrinking it would cut throughput. Horizontally, workers are identical and stateless-ish (identity from hostname), so --scale worker=7 or a k8s HPA adds capacity with zero per-replica config.

Part 9 · Deployment choices

Redis configured as a queue, not a cache

The compose and k8s manifests set appendonly yes and maxmemory-policy noeviction — the exact opposite of a cache deployment (Booklet's TTS cache runs allkeys-lru). The reasoning: a cache under memory pressure should drop cold entries; a queue under memory pressure must refuse writes and page a human, because "evicted" here would mean "silently deleted someone's job". Same technology, opposite configuration, because the data means the opposite thing.

Scratch images, and what they cost

One multi-stage Dockerfile builds any binary into a FROM scratch image: the static binary, CA certificates, a numeric non-root user — ~15MB, no shell, no package manager, no CVE surface beyond the binary. The cost is documented where it bites: no shell means no docker exec debugging and no compose healthcheck exec, so compose gates on the stores' health and Kubernetes uses httpGet probes (which need nothing inside the container).

The probe split that saves fleets

Liveness (/healthz) is process-local and dependency-free on purpose: it answers "can this process run code", and restart is the only cure for failing it. Wiring the database into liveness turns a Postgres blip into a full API fleet restart — a recoverable dependency outage converted into an outage of everything. Readiness (/readyz) is the different question — "can this instance serve right now" — and checks both stores, bounded.

Part 10 · A history of mistakes

Every one of these shipped to a branch, was caught by a test or a measurement, and taught something. They're kept because a project that documents only its successes is documenting half of what happened.

Bug 1 · The panic outcome that never was
The design defined OutcomePanicked; the classifier never produced it. A recovered panic surfaced as a plain error, classified generically retryable — the attempt history lied about panics. Caught by the integration test asserting history reads panicked → completed. Lesson: an enum value nothing routes to is a claim, not a feature; test the history, not the intention.
Bug 2 · Cancellation read from the wrong context
The runner captured context.Cause() from the pool's context, but the heartbeat cancels the execution context. Cooperative cancels recorded as generic failures, and cancelled jobs went to RETRYING instead of CANCELLED. With nested contexts, which context you interrogate is a correctness decision, not a style one.
Bug 3 · json.Unmarshal merges maps — the bench that waited forever
The bench's drain loop unmarshalled each poll into a shared struct. encoding/json merges into existing maps: when jobs finished and their statuses vanished from the response, the stale PENDING: 15 entry survived — and the bench waited forever for 15 jobs that had completed a minute earlier, while psql showed a clean table. Fresh struct per poll. The debugging path (two simultaneous readers of the same endpoint disagreeing) is the part worth remembering.
Bug 4 · Evicting a session didn't sever its stream
The control hub's first reconnect test hung: eviction deleted the map entry but left the gRPC stream open, so the client never learned anything was wrong and never reconnected. Sessions now carry a done channel closed exactly once; eviction actively terminates the stream. In connection registries, forgetting a connection and closing it are different operations, and only one of them tells the far end.
Bug 5 · The 413 that reported as invalid JSON
http.MaxBytesReader trips mid-decode, so an oversized payload surfaced as 400 invalid_json. "Your payload is too big" and "your JSON is broken" demand different client fixes; the API now detects *http.MaxBytesError and answers 413 with the limit.
Bug 6 · Testing Postgres's pretty-printer by accident
Store tests compared payloads byte-for-byte; jsonb canonicalizes ({"n":1} → {"n": 1}) and the tests failed while the code was right. Comparisons became semantic. Asserting on an exact serialized form couples the test to a formatting choice nobody made.
Bug 7 · The ghost entry in the DLQ test
A test claimed a job through the store directly, without consuming its queue delivery — then counted queue depths and found one entry too many: its own ghost. Test setups that bypass half the pipeline create states the real system never produces. The fix consumed the delivery the way a real worker would.
Bug 8 · Integer math in the reviewer's head
An autoscaler test expected 9 + 9/2 = 14. Go says 13. The test was wrong, the code was right, and the lesson is old: when a test disagrees with arithmetic, check the test's arithmetic first.

Part 11 · Glossary, in plain words

TermPlain meaning
Consumer group / PELRedis's built-in ledger of "handed out but not yet finished". Reading moves an entry into the pending-entries list; acknowledging removes it. The PEL is Forge's in-flight set — nothing hand-rolled.
Visibility timeoutHow long a handed-out job stays invisible to other workers before the system assumes its holder died and offers it again. In Forge: XAUTOCLAIM with a minimum idle time.
LeaseTime-boxed permission to work on a job, renewed by heartbeat while work genuinely runs. Silence past the TTL is how death is detected without anyone saying goodbye.
Fencing tokenA counter bumped on every ownership change, presented with every write. A worker that lost its lease holds a stale token, so its late write matches nothing. Turns "the job ran twice" into "the result was written once".
At-least-onceThe honest delivery guarantee: nothing is lost, but duplicates can happen (crash after doing the work, before acknowledging it). The pairing that makes it safe is idempotent handlers.
IdempotencyDoing something twice has the effect of doing it once. Submission-side: same (type, key) returns the original job. Execution-side: fenced writes. Handler-side: the handler's own responsibility, with job id + attempt number provided as the dedupe coordinates.
BackpressureRefusing to take on more than you can handle, so overload queues where it's visible instead of hiding in buffers until something bursts. In Forge: fetch never exceeds free slots.
Dead-letter queueWhere jobs go after exhausting retries — parked with full history, inspectable, requeueable. The alternative to a DLQ is an infinite retry loop or silent loss.
Full jitterBackoff drawn uniformly from [0, ceiling) so simultaneous failures retry spread out instead of in synchronized waves.
Lease epoch vs. wall clockClocks answer "how long"; epochs answer "who currently owns". Recovery needs both: the clock to suspect death, the epoch to make the suspicion safe when it's wrong.
